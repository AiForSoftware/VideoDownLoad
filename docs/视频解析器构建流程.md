# 视频解析器构建流程（抖音 / B站 / YouTube 实战档案）

> **读者**：未来接手本项目的大模型（或工程师）。
> **目的**：三个已验证解析器（抖音、B站、YouTube）的**完整攻关过程、核心算法、请求流程、踩坑记录**全部沉淀在此。
> **最重要的用法**：当某个解析器失效时，**不要从零推理**——先查对应档案的「失效症状对照表」，绝大多数失效都在表中有一一对应的修复路径。

## 1. 引擎契约（所有解析器共用的地基）

动手改任何解析器之前，必须理解这四层契约，否则会破坏链路而不自知：

### 1.1 解析器契约（BaseVideoClient 子类）

```python
class XxxVideoClient(BaseVideoClient):
    source = 'XxxVideoClient'          # 类名 = 配置键（allowed_sources / per_source_cookies）
    def parsefromurl(self, url, request_overrides=None) -> list[VideoInfo]:
        ...                             # 返回 1~N 个 VideoInfo（N=画质档位数）
    @staticmethod
    def belongto(url, valid_domains=None) -> bool: ...
```

- `parsefromurl` 挂 `@useparseheaderscookies` 装饰器：登录 Cookie（`per_source_cookies.<类名>`）与代理自动注入 `request_overrides`。
- 失败时返回**一个带 `err_msg` 的 VideoInfo**，不要返回空列表或抛异常到 UI。
- 新增 .py 无需改打包配置（`build.spec` 的 datas walk 自动覆盖）。

### 1.2 VideoInfo 条目契约（易错点）

| 字段 | 说明 |
|---|---|
| `download_url` | 直链。画质条目每个一条 |
| `title` | **必须带画质后缀**（`标题_4K` / `_1080P60` / `_720P` …），前端按后缀正则分组并做默认画质选择 |
| `quality` | 档位标签字符串（`4K`/`1080P+`/`1080P`/`720P`…），前端 `qualityRank` 依赖它 |
| `audio_download_url` / `audio_save_path` / `audio_ext` / `default_audio_download_headers` / `default_audio_download_cookies` | **五件套必须成套设置**。漏 `audio_save_path` → 合并下载器 `touchdir('')` → `WinError 3`（B站踩过，YouTube 照抄） |
| `identifier` | 去重/追踪键，建议 `{vid}-{label}` |
| `ext` | dash 的 m4s 会由下载层自动改写为 mp4，无需手动处理 |

### 1.3 下载管线（解析器只管给 URL，下载层自动分派）

- 无 `audio_download_url` → 单文件直下（requests 流式）。
- 有 `audio_download_url` → `_downloadwithnaiveallinone`：视频、音频分别下载 → ffmpeg 三连合并尝试（copy/transcode）→ 本地合并文件。
- m3u8/mpd → ffmpeg / N_m3u8DL-RE 分派（按扩展名）。
- **ffmpeg 合并读的是本地文件**，所以直链只要"能被下载器拉下来"即可，与 ffmpeg 无关。

### 1.4 前端画质契约

- 分组键 = 标题去掉画质后缀的基名；默认选择 = `pickDefaultQualitySelection`（指定画质向下兼容、best 取每组最高、auto 才全选）。
- 未知档位标签（如 `240P`）前端会回退到组内第一项，可放心使用。

## 2. 通用修复 SOP（失效时按此流程走）

```
① 复现：写独立诊断脚本直调解析器（模板见附录 A），不要靠 UI 猜。
② 定位阶段：
   a. 风控墙：playability=LOGIN_REQUIRED / UNPLAYABLE / "The page needs to be reloaded" / B站 412 / 抖音无 play_addr
   b. 签名失效：接口 412/-404/w_rid 校验失败/请求密钥变更
   c. 数据裁剪：响应正常但缺 dash/streamingData/档位
   d. CDN 门控：直链 403（text/plain）——区分"客户端被门控"与"参数缺失"
③ 交叉验证（最高价值一步）：跑 `yt-dlp -F <url>`。
   - yt-dlp 能拿到 → 问题是"我们的客户端配置过时"，去读 yt-dlp 源码里对应客户端的最新配置抄过来；
   - yt-dlp 也拿不到 → 平台全局收紧（如强制 poToken），走浏览器兜底或评估外置基建。
④ 修复手段优先级：换客户端/改 clientVersion > 修签名 > 真浏览器兜底 > 外置 poToken 基建（最后手段，见 YouTube 档案的失败清单）。
⑤ 端到端验证：解析 → 每档直链 Range 探测 → 真实下载一条 → ffprobe 确认音视频轨 → 重建 dist → startup.log 三锚点
   （`webview page loaded` / `window shown after successful load` / `engine ready`）。
⑥ 同步更新本档案与 AGENT_BUILD_GUIDE.md §4.4。
```

**反复被验证的元经验**：
- **永远不要信任"格式声明"，每个档位用真实请求探测可用性**（YouTube 的探测过滤就是这么救场的）。
- **客户端版本号是消耗品**：`VISIONOS/1.02`、`ANDROID_VR/1.60.19` 都有失效日。yt-dlp 的 `extractor/youtube/_base.py`（INNERTUBE_CLIENTS）是目前唯一持续维护的客户端配置参考源。
- 风控是**时变的**：瞬态 403 突发很常见，探测/请求必须带重试；但"重试后仍稳定 403"= 真门控，不要无限重试。
- 日志分级纪律：诊断步骤用 info（`[DIAG xxx]` 前缀），error 只给真实失败（UI 日志面板会全屏标红）。
- **UI 按钮"点了没反应"先查 desktop.log 的 unhandled promise rejection**：pywebview 桥接调用的 Python 异常走这条通道（startup.log 同步镜像），而不是引擎日志。实例：设置页"打开配置目录"报 `VideoDlService has no attribute 'configpath'`——`configpath` 实际是 `Config` 类的 staticmethod，桥接层调错了类；修为 `Config.configpath()`。

## 3. 抖音解析器档案（已验证）

**文件**：`engine/vd/modules/sources/douyin.py`（约 125 行，刻意保持精简）
**范围**：视频（`/video/{id}`、主站 `jingxuan?modal_id=`、`v.douyin.com` 短链）。图文笔记（`/note/`）不在已验证范围。

### 3.1 请求流程

```
URL → 提取 aweme_id
  ├─ jingxuan 模态页: 正则 modal_id=(\d+)
  └─ 其他: GET(allow_redirects=False) → Location 头 → 第一个数字串
          (无 Location 再 GET(allow_redirects=True) → resp.url 取数字)
→ 候选源顺序（关键设计）:
  ① 原始 URL（主站 SSR；带登录 Cookie 时直接含 play_addr）
  ② https://www.iesdouyin.com/share/video/{vid}（分享页；未登录常被反爬裁剪）
→ 每个候选源:
  GET → 正则 window\._ROUTER_DATA\s*=\s*(.*?)</script> (re.S|re.I)
      → 去尾部分号 → json_repair.loads（容忍脏 JSON）
      → loaderData → 遍历找 videoInfoRes.item_list[0]（或 aweme_detail）
      → 验证 video.play_addr.uri 存在（防空壳页）→ 命中即停
→ 拼 play 直链 = http://www.iesdouyin.com/aweme/v1/play/?video_id={uri}&ratio={r}&line=0
→ 画质档位枚举（2026-09-05 新增）: ratio ∈ {default(主码率，标1080P), 720p, 540p}
  （每档一个 VideoInfo 条目；FileTypeSniffer 探测可用才产出，探测全挂则强制
   产出 default 一条兜底；ratio=1080p 仍然禁止——低码率转码档，见 3.2）
→ 每档 title 带 _1080P/_720P/_540P 后缀（前端按后缀分组，下载前可选低清晰度）
```

### 3.2 核心算法与已验证事实

| 项 | 结论 |
|---|---|
| **ratio 参数** | **必须 `ratio=default`，禁止 `ratio=1080p`**。实测同视频：1080p 档 301kbps（CDN 保留的低码率转码，画质很差），default 档 718kbps（播放器实际使用的主码率，同分辨率 2.4 倍码率）。这就是"下载的比 App 里看到的糊"的历史原因。 |
| **低清晰度片源（2026-09-05 新增）** | CDN 对同一 video_id 支持 `ratio=720p`/`540p` 转码档（实测三档均 200 + video/mp4，大小比合理：720P ≈ 340MB vs 540P ≈ 332MB vs default 全片）。枚举为独立条目供用户选档（流量/体积优先场景），探测不可用的档自动剔除 |
| **码率档位表** | SSR 数据里**没有** bit_rate 档位表，不要去找（已确认不存在）。 |
| **UA** | 解析/下载都用 iPhone Safari UA（iOS 16.0）。 |
| **登录态** | 未登录时主站/分享页都会被裁剪掉 `play_addr`——这是"解析失败"的最常见原因，不是代码 bug。错误信息里会引导用户去【设置】页登录（`per_source_cookies.DouyinVideoClient`）。 |
| **json_repair** | ROUTER_DATA 尾部可能带 `;` 或脏字符，用 `json_repair.loads` 而非 `json.loads`。 |

### 3.3 踩坑记录

| # | 现象 | 原因 | 修复 |
|---|---|---|---|
| 1 | 下载画质明显比 App 播放糊 | `ratio=1080p` 命中 CDN 低码率转码档 | 改 `ratio=default`（见 3.2） |
| 2 | 未登录时解析必失败 | SSR 被反爬裁剪，无 play_addr | 双候选源（主站→分享页）+ 明确错误提示引导登录；登录后主站直出 |
| 3 | jingxuan 模态页解析不到 | modal_id 才是 aweme_id，直接 GET 原链接拿不到视频数据 | 优先正则提取 modal_id |
| 4 | 早期用 aweme detail API 的尝试全部失败 | `/aweme/v1/detail` 类接口需要 msToken/X-Bogus 签名 | **放弃 API 路线，全面走 SSR 页面解析**——这是本解析器的根本设计决策 |

### 3.4 失效症状对照表

| 症状 | 嫌疑 | 动作 |
|---|---|---|
| 全部视频解析失败，错误含"未能从抖音页面提取到 video.play_addr.uri" | 未登录（Cookie 过期）或 ROUTER_DATA 结构变更 | ① 先让用户登录重试；② 仍失败→诊断脚本看 ROUTER_DATA 是否存在/结构（loaderData 键名、videoInfoRes 路径是否变了）；③ 若是抖音改版，跟进前端路由结构 |
| **页面 200 但无 _ROUTER_DATA、无 title、body 为空，仅一段 `_$jsvmprt` 混淆 VM 脚本（2026-09-05 实锤）** | 抖音对**无登录 Cookie** 的请求直接下发 JS 虚拟机风控挑战页（acrawler 前置），SSR 数据完全不下发 | 不是代码问题——引导用户在「登录态」弹窗做抖音登录，Cookie 就位后 SSR 恢复正常。勿尝试正面破解 JSVM 签名（成本极高且随时失效） |
| 解析成功但下载 403/极慢 | iesdouyin 播放接口风控 | 诊断脚本直 GET download_url 看状态码；必要时给播放接口补 Referer 或换 line 参数 |
| 画质变糊（复发） | 有人把 ratio 改回了 1080p | 检查 download_url 里 `ratio=default` |
| 短链 v.douyin.com 失败 | 重定向逻辑变化 | 诊断脚本打印 Location 头内容，核对正则 |
| 解析只产出一条条目 / 低清晰度档消失 | 画质档位枚举回归（被人精简 `_ratios` 循环） | 检查 parsefromurl 尾部档位枚举是否在（default/720p/540p 三档探测 + 兜底）；注意探测不可用的档会被剔除，属正常现象 |

## 4. B站解析器档案（已验证）

**文件**：`engine/vd/modules/sources/bilibili.py`
**范围**：普通视频（BV）、bangumi（ep/ss）、cheese、festival 链接；dash 高画质 + 音轨合并。

### 4.1 请求流程

```
URL → 提取 bvid/cid
  ├─ 元数据: x/web-interface/wbi/view（WBI 签名，绕 412 风控）→ data.pages[].cid
  │         失败 → 未签名 x/web-interface/view（旧接口兜底）
  ├─ playurl（两级）:
  │  ① 主路径——真实浏览器（DrissionPage 无头 Edge）:
  │     注入登录 Cookie(.bilibili.com) → page.get(播放页) → 等待 ~4s
  │     （B站前端自行 bootstrap 播放器 + 生成 bili_ticket + 发出 playurl XHR）
  │     → 从 performance 时间线读出 playurl 请求 URL → 在页面内原样回放该 XHR
  │       （复用页面自己的 Cookie 与 WBI 签名）→ 拿到含 4K/8K/HDR 的 dash
  │     （CDP listen('api.bilibili.com') 仅作兜底——见踩坑#1/#2）
  │     （浏览器 probe 每 URL 只跑一次：多 P 视频首个 cid 走①，
  │       其余 cid 直接走② requests 路径——防解析风暴，见踩坑#7）
  │  ② 回退——requests 直调 x/player/playurl（自己 WBI 签名 + bili_ticket + web_location）
  ├─ dash 枚举: dash.video[] 按档位枚举条目（quality 标签 + 标题后缀），
  │             音轨选最高码率 → audio 五件套 → 合并下载
  └─ 安全网: 全部失败 → 浏览器再抓一次 → 固定产出一条 720P(durl) 条目
            （"不能解析就至少给 720p"）
```

### 4.2 核心算法

**WBI 签名**（模块级实现，登录/未登录都做）：
1. `GET x/web-interface/nav` → `wbi_img.img_url/sub_url` → 取文件名得 `img_key`/`sub_key`（未登录也能拿，结果缓存）。
2. 固定混淆表 `_BILI_WBI_ENC_TABLE`（64 元素）→ `mixin = ''.join((img_key+sub_key)[i] for i in table)[:32]`。
3. 参数加 `wts=int(time.time())` → 过滤值中 `!'()*` 字符 → 按 key 排序 urlencode → `w_rid = md5(query + mixin)`。

**playurl 参数**（决定能不能拿到高画质）：`otype=json&fnver=0&fnval=16&fourk=1&bvid&cid&platform=html5`，有 bili_ticket 时追加 `bili_ticket` + `web_location=playurl`，然后整体过 `_bili_sign_wbi`。`fnval=16` = 要 dash；`fourk=1` = 允许 4K；**实际档位上限由 Cookie 的会员等级决定**。

**浏览器回放机制（本项目最重要的原创设计）**：
- **主路径是 performance 时间线**：`performance.getEntriesByType('resource')` 里记录了播放器自己发出的 playurl 请求 URL——不管我们的监听器是否工作它都会被记录。拿到 URL 后**在页面内**原样回放（复用页面的 Cookie/WBI 签名/风控上下文）。
- **CDP 网络监听只是兜底**：异步生效、会被媒体分片淹没、风控时序随机。
- **等待期间绝不 reload 页面**。

### 4.3 踩坑记录（每条都是真实返工）

| # | 现象 | 原因 | 修复/结论 |
|---|---|---|---|
| 1 | 50 秒等不到 playurl 包，等待循环无任何诊断 | ① 监听匹配串过时：实际接口已是 `/x/player/wbi/playurl`，旧代码匹配 `/x/player/playurl` 字面量匹配不上；② `window.__playinfo__` 已被 B站下线（undefined），不要指望它 | 监听放宽为 `api.bilibili.com`；数据获取改 performance 时间线回放 |
| 2 | reload 后更糟 | B站风控引导（gaia 指纹）会把 playurl 拖到 ~30s，reload 等于重来 | **等待中禁止 reload** |
| 3 | dash 条目下载崩：`WinError 3: ''` | 设置 `audio_download_url` 时没成套设置 `audio_save_path` 等，合并器 `touchdir(dirname(''))` | **audio 五件套必须成套**（枚举条目与 720P 兜底条目两处都修了） |
| 4 | 匿名只有 720P(durl)，"连 720p 都没有"过 | 旧代码有 `SESSDATA in cookies` 守卫，匿名直接跳过浏览器路线 | 浏览器路线**始终尝试**（匿名也有 bili_ticket 生成，只是档位低）；Cookie 决定上限 |
| 5 | 未签名 view 接口 412 | B站对未签名 `x/web-interface/view` 上风控 | `_bili_view` 改走 WBI 签名的 `wbi/view`，未签名仅作兜底 |
| 6 | 已登录仍被降到 720P | playurl 缺 `bili_ticket` + `web_location` | 参数自动纳入（见 4.2）；Cookie 过期的典型症状就是"解析正常但只有 720P"，引导重新登录 |
| 7 | 多 P 视频解析"卡死"十几分钟（8 分 P 实测，UI 无进度） | 分 P 循环里对**每个 cid** 都串行跑一次无头浏览器 probe（每次 10~60s），8 P = 十几分钟无任何进度 | `_browser_probe_done` 标志：浏览器 probe **每 URL 只跑一次**（首个 cid），其余分 P 直接走② requests 路径；验证：8 分 P 视频 11.9s 全部解析完（多 P 的 requests probe 拿不到 dash 时会产出 720P(durl) 条目，可用性不受影响） |
| 8 | 用户听到"后台自动播放解析的视频"（无头模式不该有声音） | `--headless=new` 是**完整浏览器**，B站播放器自动播放（这正是 playurl XHR 的触发机制），部分版本把解码声音直接输出到音频设备 | `co_hook_func` 注入 `--mute-audio`（播放照常、声音静默）+ `--autoplay-policy=no-user-gesture-required`（确保自动播放不被浏览器策略拦掉）。**切勿禁 autoplay**——playurl XHR 靠它触发，禁了 dash 就拿不到 |

### 4.4 失效症状对照表

| 症状 | 嫌疑 | 动作 |
|---|---|---|
| **多 P 视频解析极慢 / 像卡死**（单 P 正常） | 浏览器 probe 回归成"每 P 一次" | 查 `[DIAG bilibili]` 日志：一次解析只应有**一条** `browser fetch START`；若每 P 一条 → `_browser_probe_done` 标志被人删了 |
| 全部降级 720P(durl) | Cookie 过期 / playurl 参数风控升级 | 先引导重新登录；仍不行→诊断脚本核对 bili_ticket 是否进参、wbi 签名是否被接受（-404/-412 码） |
| 浏览器路线超时 | 播放器 bootstrap 变慢 / 回放 URL 提取失效 | 看 `[DIAG bilibili]` 日志：browser fetch START→settling→DONE 各步耗时；检查 performance 时间线里 playurl URL 是否还能找到 |
| wbi 签名全部 -403/-404 | **混淆表 `_BILI_WBI_ENC_TABLE` 变更**（B站偶尔换表） | 从 B站前端 JS（`web_interface` 相关 chunk）重新提取混淆表更新 |
| dash 有了但合并失败 | audio 五件套不齐（回归） | 检查条目构造代码是否被人精简 |
| 8K/HDR 缺失 | fnval 位掩码需求变化（8K 需要 fnval=128 等） | 查 B站 API 文档更新 fnval；注意 fourk=1 已含 |

## 5. YouTube 解析器档案（已验证，2026-09 全量重写）

**文件**：`engine/vd/modules/sources/youtube.py` + `engine/vd/modules/utils/youtubeutils.py`（新增 VISIONOS 客户端）
**设计对标**：Tyrrrz/YoutubeDownloader 的核心思路（InnerTube 多客户端轮换 + 画质枚举 + 明文直链优先）。

### 5.1 请求流程

```
URL → _extractvid（v= 参数 / youtu.be / shorts / embed / live 路径段）
→ _innertube（2 轮轮换）:
   第 1 轮: YouTube(client='VISIONOS')，失败自动内嵌轮换 fallback_clients 池
            ['ANDROID','ANDROID_VR','ANDROID_MUSIC','ANDROID_CREATOR',
             'ANDROID_TESTSUITE','ANDROID_PRODUCER','ANDROID_KIDS','WEB_EMBED','TV','IOS']
   第 2 轮（仅当第 1 轮全灭）: RequestWrapper.reset_curl_session() 换新会话 + 3s 退避
   每次尝试记 [DIAG youtube] Innertube[client]=status(reason) streams=bool
→ 仍被墙 → 浏览器兜底（无头 Edge，注入 YouTube 登录 Cookie）:
   读 window.ytInitialPlayerResponse（或 HTML 正则）
→ _builditems（直接从 raw streamingData 构条目，不走 fmt_streams）:
   formats(渐进式) 优先占档 → adaptiveFormats 补高档（无渐进式时低档也补）
   → 音轨选择: 默认轨('original') > mp4 容器 > 最高码率
   → 过滤 is_otf/issabr/无 url 流
→ Range 探测过滤: 每个候选视频流+音轨用 'Range: bytes=0-' 实测，
   403(text/plain) 档位剔除并打 warning（用户只会选到真能下载的档位）
→ 低分辨率兜底: 全被过滤/只有 240P 的老视频仍保证产出 ≥1 条
→ 每档一个 VideoInfo（自适应档带 audio 五件套，走 ffmpeg 合并）
```

### 5.2 核心算法

**VISIONOS 客户端（本解析器成立的前提，务必完整保留）**：

```python
'VISIONOS': {
    'innertube_context': {'context': {'client': {
        'clientName': 'VISIONOS', 'clientVersion': '1.02',
        'deviceMake': 'Apple', 'deviceModel': 'RealityDevice17,1',
        'userAgent': 'Mozilla/5.0 (Macintosh; Intel Mac OS X 15_7_3) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/26.0 Safari/605.1.15',
        'osName': 'visionOS', 'osVersion': '26.5.23O471'}}},
    'header': {...同 UA..., 'X-Youtube-Client-Name': '101', 'X-Youtube-Client-Version': '1.02'},
    'api_key': 'AIzaSyAO_FJ2SlqU8Q4STEHLGCilw_Y9_11qcW8',
    'require_js_player': False, 'require_po_token': False,
}
```

- 关键点：`clientVersion: 1.02`（刻意旧版）+ `INNERTUBE_CONTEXT_CLIENT_NAME=101` → **不在 GVS poToken 策略内**，返回完整自适应梯子的明文 https 直链（无签名加密、无需 n 变换、无需 pot）。
- 副作用：VISIONOS 是**纯自适应清单**（没有 progressive 音视频合一格式），所以所有档位都走"视频+音轨 ffmpeg 合并"，audio 五件套是生命线。
- VISIONOS 优先 + ANDROID 等兜底：ANDROID 目前只剩 360P progressive（itag18）能下，但作为轮换兜底没有成本。

**画质标签映射**（`_qualitylabel`）：≥4320→8K、≥2160→4K、≥1440→1080P+、≥1080→1080P60/1080P（fps>30）、≥720→720P60/720P、≥480→480P、≥360→360P、≥240→240P、其余→144P。

**自适应档位阈值自适应**：有渐进式计划时 adaptive 只补 ≥1080 的档位（避免和渐进式抢同档）；无渐进式（VISIONOS 就是）时 adaptive 覆盖 ≥360。

**下载头**：`Range: bytes=0-` 固定进 `default_download_headers`（对全部档位无损，开放范围=全量 206）。

### 5.3 攻关史与失败清单（最有价值的一节——这些路都走过，别再走）

| 阶段 | 现象 | 结论 |
|---|---|---|
| 初始症状 | 所有 Innertube 客户端间歇性返回 `LOGIN_REQUIRED(Sign in to confirm you're not a bot)` | 多客户端轮换只能碰运气，且换不来高画质 |
| 客户端普查 | ANDROID_VR/ANDROID_MUSIC/ANDROID_CREATOR/ANDROID_TESTSUITE/ANDROID_PRODUCER/TV/WEB_EMBED 全部 `UNPLAYABLE(The page needs to be reloaded)`；IOS 400 Bad Request（clientVersion 过旧）；WEB OK 但 0 流 | ANDROID 一度是唯一活口 → 只能 360P(itag18) |

| 解签路线 | 旧 fmt_streams/Cipher 的 sig/nsig 函数名正则在当前播放器构建（f572e43c）上**全部失配**（`getsigfunctionname` 空 message 异常）；且实测 ANDROID 明文直链**根本不需要** n 变换/解签 | **fmt_streams/Cipher 整体绕开**，直接从 raw streamingData 构条目 |
| googlevideo 行为 | 无 Range 的普通 GET 可能 403（带 Range 206）；短时高频请求会触发**瞬态 403 突发**（重试即恢复）；而门控流是**重试后仍稳定 403** | Range 固定进下载头；探测带 1 次重试防误杀 |
| 交叉验证破局 | `yt-dlp -F` 能拿全梯子 → 读它源码发现 `_DEFAULT_CLIENTS = ('visionos', 'web')` → 抄配置 | **yt-dlp 源码是客户端配置的唯一持续维护参考源** |

## 6. 腾讯视频解析器档案（已验证，2026-09-10 实测通过）

新增 `engine/vd/modules/sources/qq.py`（`TencentVideoClient`），支持 `v.qq.com/x/cover/...` 与 `/x/page/...`。
**模块名用 `qq` 而非 `vqq`**：懒加载匹配规则是 `module_name in hostname`（`sources/__init__.py::_EAGER_PARSERS`），
hostname 是 `v.qq.com`，`vqq` 不是其连续子串且模块名不能含点，否则解析器一次都不会被加载（同 §7.3#1 的坑，平台无关）。

### 6.1 请求流程
1. 从 URL 提取 `vid`：正则 `/([a-zA-Z0-9]{11,})\.html` 匹配 `.html` 前的最后一段（cover 段 `mzc00200seo6p1w` 不带 `.html`，天然不会误匹配）；
   无 `.html` 后缀的 `/x/page/<VID>` 取路径最后一段，并过 `^[a-zA-Z0-9]{11,}$` 校验，避免误吞 cover id。
2. `getinfo` 接口：`https://vv.video.qq.com/getinfo?vid=<vid>&platform=101001&charge=0&otype=json&defn=<defn>&dtype=1&sdtfrom=v1010&host=v.qq.com`
   —— **当前实测无需 `ckey`**，直接返回 `QZOutputJson`，含 `vl.vi[0].fn` / `fvkey` / `ul.ui[0].url`。
3. 先探一次 `defn=shd` 拿 `fl.fi`（该片源**真实可用的清晰度列表**），再逐档 `getinfo` 取 `fn`+`fvkey`，按直链去重。
4. 直链拼装：`ul.ui[0].url + vi.fn + '?vkey=' + vi.fvkey`，下载头带 `Referer: https://v.qq.com` 与登录 Cookie。

### 6.2 核心算法与已验证事实
- **清晰度按接口真实档位枚举，绝不硬编码**：实测某片源只有 `hd(480P)` / `shd(720P)`；
  若硬编码 `fhd/shd/hd/sd`，腾讯会把不支持的档位**降级返回同一地址**，导致列表出现重复条目。
  做法：读 `fl.fi[].name`（与 `resolution`），逐档请求，按 `download_url` 去重（`seen` 集合）。
- `title` 必须带画质后缀（`标题_720P`），否则前端画质分组/默认选择失效（见 §1.2）。
- 单段片源：直链即完整视频。`fn` 形如 `a.p201.1.mp4`（多段）时未做分段拼接，取不到完整地址会回落 `WebMediaGrabber`。

### 6.3 踩坑记录（每条都实测过）
| 现象 | 根因 | 修法 |
|---|---|---|
| 解析返回 cover id / 永远解析失败 | VID 正则跨不过 `cover` 后的 `/` | 改为匹配 `.html` 前最后一段（见 6.1） |
| 同一清晰度出现两条重复 | 硬编码档位 + 腾讯降级返回同地址 | 按 `fl.fi` 真实档位枚举 + 按地址去重 |
| 无 `ckey` 报鉴权失败 | 部分片源/时段需要 | 先试无 ckey，失败再带登录 Cookie 重试（接口实测目前免 ckey） |

### 6.4 失效症状对照表
| 症状 | 可能原因 | 排查 |
|---|---|---|
| `belongto` 不命中 | 链接非 `v.qq.com` | 确认 hostname；`qq.com` 根域不算（会误吞 `weixin.qq.com`） |
| getinfo 返回空 `vl` | vid 提取错（见 6.3） | 诊断脚本打印提取出的 vid 比对 |
| 全部档位去重后 0 条 | 接口改了 `fl.fi` 结构 | 打印 `fl` 原样，核对 `fi[].name` |

## 7. 微信视频号解析器（2026-09-08 已移除，勿复刻）

**状态：已删除。** 文件 `weixin.py` / `weixin_mitm_capture.py` / `weixin_wasm_keystream.js` /
`wasm_video_decode.{js,wasm}` 及其全部调试脚本、`_samples/` 逆向素材均已删除；
`sources/__init__.py::_EAGER_PARSERS` 中的 `('weixin', 'WeiXinChannelVideoClient')` 已注销。

### 7.1 移除原因：两条支柱全部实测断裂

**支柱一 —— 拿不到直链（无登录态）。** 以真实分享链接 `https://weixin.qq.com/sph/A7gl6IJhQZ`
实测 4 条路径，全部失败：

| 路径 | 实测结果 |
|---|---|
| 分享页 HTML（桌面 / iPhone / 微信内置 三种 UA） | 均为 **2463 字节 SPA 空壳**，`videoUrl`/`decodeKey`/`objectDesc` 全部未命中 |
| `finder-preview/pages/sph?id=` 落地页（三种 UA） | 同上空壳 |
| `POST get_feed_info`（5 种组合：基础、移动UA、微信UA、带 scene、带 objectId） | `errCode=0` 但 `feedInfo` **恒定只有 9 个卡片元数据字段**：`picInfo, description, favCountFmt, likeCountFmt, forwardCountFmt, commentCountFmt, createtime, isHardAd, coverUrl` —— **永远不含** `videoUrl` / `decodeKey` |
| 3 个候选接口（`finderweb`、`mmfinderassistant`、`cgi-bin/mmfinderwxaservlet`） | 全部 `errCode:-1 Cannot POST` |

结论：**微信在无登录态下根本不下发视频直链**，这是平台侧硬限制，不是代码 bug。

**支柱二 —— 解密算法从未被还原。** 用真实样本对（`wx_encrypted.mp4` +
`decode_key="2136343393"`）跑 **10 种 ISAAC64 seed 布局 × 2 种 keystream 方向**
（rsl0_dk_others0 / rsl_all_dk / splitmix256 / byte_loop / rsl0_dk_repeat8 × reverse/normal），
**20 种组合全部 `no ftyp`**，无一解出合法 MP4 头。原先的"wasm + Node 桥接"只通过了
合成数据往返自测，从未通过真实样本（原档案里也承认样本并非配套对）。

→ 既拿不到直链、也解不开密文；唯一剩余路径是让用户装 mitmproxy + 装 CA 证书 +
登录微信 PC 客户端手动抓包，与本项目"开箱即用"定位冲突。**故整体移除。**

### 7.2 如果将来要重做，必须先确认这两件事

1. 先拿到**带 `key` / `_fid` 的完整分享链接**（非 `/sph/<id>` 短链）实测接口是否下发直链；
   短链形式经实测确认无解。
2. 先逆向出 `wasm_video_decode.wasm` 里 `WxIsaac64` 的 **seed 布局与 keystream 方向**，
   并用真实样本解出 `ftyp`，再谈实现。注意：类名为 64，但内部实为 **ISAAC32**
   （i32 指令，mix 移位 13/6/2/16）——纯 ISAAC64 复刻这个方向本身就是错的。

在这两点有确定结论之前，**不要**重新引入微信解析器。

### 7.3 残留但可复用的经验

| # | 经验 | 说明 |
|---|---|---|
| 1 | **新增解析器时，模块名必须是 hostname 的子串** | 懒加载匹配表 `sources/__init__.py::_EAGER_PARSERS` 的规则是 `module_name in hostname`；主机名不含下划线，命名 `weixin_channel` 会**永远匹配不到** `channels.weixin.qq.com`（曾因此解析器一次都没被加载）。★此坑与平台无关，新增任何解析器都要检查 |
| 2 | 微信系 wasm glue 是 worker 构建，Node 下需 `vm` 上下文 | 硬编码 `ENVIRONMENT_IS_WORKER=true`，且顶层 `var Module = ...` 会自建空 Module 遮蔽 `instantiateWasm`；需改写为优先引用 `globalThis.Module` |
| 3 | 解密类操作必须"校验通过才写回" | 解出的数据必须过魔数校验（如 `ftyp`）才落盘，绝不用错误 keystream 写坏用户文件。这条设计是对的，值得在其它解析器沿用 |

## 8. 维护优先级与前瞻

1. **客户端版本号是最容易失效的点**（YouTube VISIONOS/1.02、B站混淆表、抖音接口形态）。每次失效先怀疑它们，先查 yt-dlp。
2. **不要引入的复杂度**：外置 poToken 基建（已验证无效且维护成本极高）、CDP 网络监听作为主路径（performance 回放更稳）、再给 YouTube 加回 JS 解签（已死且不必要）。
3. **新增平台解析器**时，直接复用本章模式：SSR/API 双候选 → 风控探测 → 画质枚举+探测过滤 → audio 五件套 → 安全网条目 → 本档案加一节。
4. 任何解析器改动后：真实链接端到端 + 重建 dist + 三锚点 + 更新 `AGENT_BUILD_GUIDE.md` §4.4 与本档案。
